# 1 — Two Sum (예시, 실제 커밋 대상 아님)

- **날짜:** —
- **링크:** https://leetcode.com/problems/two-sum/
- **난이도:** Easy

> 이 파일은 STAR writeup 형식·깊이를 보여주는 참고용 예시다. 실제 문제 풀이 커밋에는 포함하지 않는다.

## 풀이

```python
class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        seen = {}
        for i, num in enumerate(nums):
            complement = target - num
            if complement in seen:
                return [seen[complement], i]
            seen[num] = i
        return []
```

## S — Situation (문제가 뭔가)
정수 배열 `nums`와 target 값이 주어질 때, `nums[i] + nums[j] == target`을 만족하는 서로 다른 두 인덱스 `i, j`를 찾는다. 정답은 정확히 하나 존재한다고 가정하며, 같은 원소를 두 번 쓸 수 없다. N은 최대 10^4 수준.

## T — Task (왜 까다로웠나)
Brute force로 모든 쌍 `(i, j)`를 확인하면 O(N²)인데, N=10^4에서도 10^8 연산이라 통과는 하지만 더 나은 하한이 명백히 존재한다. 핵심 관찰: "num을 봤을 때 짝(target-num)이 이미 나왔는지"만 알면 되므로, 굳이 두 번째 루프로 나머지를 스캔할 필요가 없다 — 지금까지 본 값들을 어딘가에 기록해두고 O(1)로 조회하면 된다.

## A — Action (접근과 대안)
- **검토한 대안들:**
  - A. Brute force 이중 루프 — O(N²), 구현 단순
  - B. 정렬 + 투 포인터 — O(N log N), 하지만 원본 인덱스를 잃어버려서 별도 인덱스 배열 유지 필요
  - C. 해시맵(1-pass) — 값을 만날 때마다 `target - num`이 이미 등록돼 있는지 확인 후 자신을 등록
- **각 대안의 트레이드오프:** A는 느리지만 공간 O(1). B는 시간은 개선되지만 인덱스 복원 로직이 추가 복잡도를 만든다. C는 시간 O(N), 공간 O(N)이며 구현도 가장 단순 — 이 문제 규모(N≤10^4)에서 공간 비용은 무시 가능.
- **최종 선택과 근거:** C(해시맵 1-pass) 선택. 배열을 한 번만 순회하며, 각 인덱스 `i`에서 "내 짝이 이미 왼쪽에 있었는가"만 물으면 되므로 별도의 2-pass나 정렬이 불필요하다. 동작 원리: `seen` 딕셔너리는 "지금까지 본 값 → 인덱스"를 유지하는 invariant를 가지며, 매 스텝에서 이 invariant를 이용해 O(1) 조회 후 갱신한다.

## R — Result (복잡도·한계)
- **시간복잡도:** O(N) — 각 원소를 한 번씩만 방문, 딕셔너리 조회/삽입은 평균 O(1)
- **공간복잡도:** O(N) — 최악의 경우 모든 원소를 `seen`에 저장
- **Correctness 근거:** 정답이 `(i, j)`, `i<j`라면, 루프가 `j`에 도달했을 때 `seen`에는 이미 인덱스 `i`까지의 모든 값이 들어있으므로 `nums[i] = target - nums[j]`가 반드시 조회된다.
- **엣지케이스:** 배열 길이 2 미만이면 애초에 문제 제약상 발생하지 않음(항상 정확히 하나의 해 존재 보장). 음수·중복값이 있어도 해시맵은 값 자체로 조회하므로 영향 없음. 단, 동일한 값이 두 번 나오는 경우(`nums=[3,3]`, `target=6`) `complement in seen` 체크가 `num` 자신을 등록하기 *전에* 이루어지므로 자기 자신과 짝짓는 문제가 발생하지 않는다.
- **한계:** 정답이 여러 개 존재할 수 있는 변형 문제(모든 쌍 반환)라면 이 방식으로는 부족 — 그 경우 값별 인덱스 리스트를 유지해야 한다.
